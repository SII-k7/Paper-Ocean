# Ubuntu 与多端记录同步可行性

后续已有 v1.1.0 最小实现，当前功能与验证见 [Ubuntu 与论文池说明](ubuntu-paper-pool.md)。本文保留为 v1.0.0 基线的研究记录。

研究日期：2026-09-08。代码基线：v1.0.0 / adf3ba3。本文为方案评估，未实现同步、部署服务或完成 Ubuntu 实机认证。设备范围暂按 Windows 与 Ubuntu 电脑；手机／平板作为扩展讨论。

## 结论

两项均可实现。Ubuntu 适配以平台补齐和验证为主；同步是新的数据与会话能力，工作量明显更大。建议先补 Ubuntu 桌面支持，再实现不含 PDF 的离线可用记录同步，最后处理跨设备继续追问。

## Ubuntu：已有基础与缺口

当前使用 Electron 43.4.0、React、PDF.js 与 Node 文件服务。平台专属下载逻辑只在 Windows 启用，其他平台使用标准 fetch；窗口在 Linux 默认使用系统边框；归档目录在非 Windows 已回退到 `~/paper`。Codex CLI 官方提供 Linux 安装方式。

需要补齐：

1. `package.json` 增加 Linux 构建命令、图标／桌面入口及 `.deb` 配置；AppImage 可作为后续便携包。electron-builder 支持两种格式。
2. `.github/workflows/release.yml` 增加 Linux 构建和产物校验。目前只有 Windows 与 macOS 打包，publish 的 Ubuntu runner 只负责发布，不是 Linux 应用验证。
3. `electron/codex-client.mjs` 补 Linux 可执行文件发现。当前 Linux 仅依赖环境变量指定路径或 PATH 中的 `codex`，从桌面图标启动时可能找不到终端中由 nvm 等管理的安装。
4. 初期支持目标建议 Ubuntu 22.04／24.04 x64；这是待验证矩阵，不是已支持声明。ARM64 单独验收。
5. 验证 Wayland／X11、中文输入法、字体、文件选择、外链登录、缩放、保存重启与归档。Ubuntu AppArmor 的用户命名空间限制可能影响沙箱启动，需按应用安装路径处理，不能以默认关闭 Chromium 沙箱或系统防护代替适配。

源码 Web 模式也是 Ubuntu 候选路径，但仍需本机 Node 与 Codex 后端；不能只部署静态前端就完成问答。

## 同步范围

| 内容 | 建议 |
| --- | --- |
| 论文标题、作者、来源、版本、分类、已读状态 | 同步 |
| 讨论标题、固定论文集合、用户问题、AI 回答 | 同步，作为跨设备权威记录 |
| 笔记正文、高亮文字、页码和坐标 | 同步 |
| 阅读页码、页内位置、对话阅读位置 | 同步最近阅读点，同时保留每设备位置；不强制跳动另一台正在阅读的页面 |
| 未发送草稿 | 按设备保留，支持取用；冲突时不覆盖 |
| PDF、整篇文字索引、页面图片、缩略图 | 第一版不同步，在本机重建 |
| 文件路径、缓存路径、下载任务、归档路径、窗口尺寸、标签布局 | 各设备独立 |
| Codex 登录凭据、运行中的请求、底层会话编号 | 各设备独立，不通过同步仓库传输 |

不传 PDF 仍会同步用户问题、AI 回答和引用摘录，其中可能包含原文内容；不能把该方案描述为“论文信息完全不离开设备”。模型请求的数据处理路径维持原设计。

## 必须解决的三个结构问题

### 1. 论文身份与本地文件解耦

`src/types.ts` 的 PaperRecord 当前把论文元数据、必填 path、阅读位置、paperDir 混在一起。服务端 Web 版本又使用本机文件句柄，不能直接搬运 Windows 资料库到 Ubuntu。

建议拆为可同步的论文／版本记录与每台设备独立的文件映射。当前内容 ID 是 SHA-256 前 24 个十六进制字符，同字节 PDF 即可匹配；即使文件名或路径不同也不影响。同标题或同 arXiv 标识不保证 PDF 内容相同，候选可以提示关联，页码与高亮绑定仍需核对版本和内容。未来可增加完整摘要，不改变旧 ID。

新设备先显示“尚未在本机下载”的论文和完整历史问答，允许导入本地文件或主动按来源下载。这个下载来自论文来源，不是设备之间同步 PDF。缺文件不能删除讨论或阻止查看历史，原文引用先提示补充对应版本。

### 2. 记录浏览与继续追问解耦

`src/App.tsx` 目前发送问题会准备本地论文上下文，并恢复 `threadsByScope` 对应的 Codex 会话；恢复失败会保留历史并停止。官方 thread/resume 面向已有存储会话，不能由“使用相同账户”推断新机器一定可恢复旧机器的编号。

建议让 Paper Ocean 的 conversationId 作为跨设备身份，本地单独映射 Codex 会话。在新设备首次追问时，明确创建本地执行会话，带入同步历史中的相关轮次及必要摘要，并由本地相同版本 PDF 重建原文上下文。标记已带入的消息版本，避免遗漏或重复注入。历史回答必须按引用数据处理，不能变为高优先级指令。

这可实现产品层面的延续，但不能承诺复刻旧会话全部内部状态；被摘要的长历史与未同步的原文页图需明确边界。没有 PDF 时，第一版允许查看历史；基于原文继续追问前要求补充 PDF，后续才考虑明确标注的“仅基于历史回答”模式。

### 3. 整体快照改为按记录同步

`electron/library-store.mjs` 的原子快照与串行写入保护单机；`server/web-server.mjs` 的 revision / 409 只拒绝旧快照覆盖，不提供自动合并。把整个 library.json 放进网盘不足以可靠同步。

建议增加持久化的离线变更队列、设备标识、操作唯一 ID、记录版本和删除标记；网络恢复后批量推送并增量拉取，重复重试必须幂等。同步入站仍经过本地串行保存与格式校验，不能绕过原有数据保护。

- 问答按唯一 ID 追加，并保存回答对应的问题、父轮次与执行设备。不同设备同时追问保留并行分支，不能只按时间拼成虚构的单一对话。
- 流式回答由产生它的设备更新；第一版优先同步完成或明确中断的结果，避免复制 pending 后在另一端被旧加载逻辑误判为失败。
- 笔记并发修改保留冲突副本；删除／归档保留版本标记，防止旧设备把内容恢复出来。
- 阅读位置不取最大页码，人会回看；按设备保留最近点，使用版本关系判断更新，不只信任设备时钟。
- 仅凭 updatedAt 覆盖所有类型不能满足上述要求。服务端需要认证、每用户授权、版本检查与传输加密；端到端加密及密钥恢复可作为独立选项评估。

## 同步载体选择

| 方案 | 适合情况 | 代价与边界 |
| --- | --- | --- |
| 用户自己的 WebDAV / Nextcloud | 个人少量桌面设备，已有私有存储，希望不依赖项目运营服务器 | 需要应用自行实现增量、合并、重试和压缩；采用每设备独立不可变批次避免竞争覆盖，不能只上传同名 JSON；具体 WebDAV 服务需实测 |
| 独立轻量同步服务与数据库 | 面向更多用户，后续增加浏览器和手机端 | 需要部署、账户、每用户数据隔离、备份和运维；可自建或使用托管数据库。Supabase 的 Auth + RLS 是候选，不在此次评估中替用户开通或绑定服务 |

建议先确定设备与已有存储条件，再选载体；论文身份、变更队列和合并规则应独立于供应商。桌面互同步不要求某台电脑一直开机，但需要双方能访问同一个存储／同步服务。

手机浏览历史可读取同一份同步记录并另做窄屏界面。手机浏览器不能直接运行当前本地 Codex 子进程，若要发起问答，还需要一台在线且已授权的电脑／后端代为执行。现有 Web 预览明确绑定本机地址和本机会话，不能通过把监听地址改成公网地址直接充当多用户服务。

## 建议交付顺序与验收

1. Ubuntu：构建包、Linux 路径发现、CI，以及至少一台真实 Ubuntu 的完整导入／问答／重启验证。
2. 同步基础：拆分元数据与路径，历史迁移、账户／存储连接、离线队列、按记录合并；验证无 PDF 也能浏览问答。
3. 连续问答：每设备执行映射、历史重建、本地版本匹配；验证换机后的事实与引用能够回查。
4. 冲突与恢复：两端离线编辑、同时追问、删除后离线端重连、网络中断重试、时钟偏移、失效凭据与迁移回滚。

本轮只完成代码与文档研究。Ubuntu 系统版本、是否含移动端及同步存储尚未最终确定，因此不作具体工期承诺。
