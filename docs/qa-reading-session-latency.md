# 论文会话隔离与问答延迟验证

日期：2026-09-12。基线为 v1.2.4，Windows，Codex CLI 0.146.0，ChatGPT 登录，GPT-5.6 Luna / max / priority（Fast），HTTP 流式传输。

## 问题与修复

Paper Ocean 原先继承用户 Codex 的插件、MCP、技能目录和跨项目记忆。即使论文文本已经完整附在问题中，模型仍会先搜索工作区记忆、读取历史记录或辅助技能。此次基线的首问发生 3 次工具调用；仅关闭 MCP/插件的试验仍有 8 次记忆文件读取，首字等待 87.6 秒。

现在仅对 Paper Ocean 启动的子进程和论文线程应用专用配置：

- 关闭跨项目记忆注入和记忆生成，避免把其他开发任务的资料带入论文回答。
- 关闭无关插件和应用连接，按当前论文目录发现并停用独立 MCP 与技能目录。
- 新建和恢复线程使用同样的配置；已加载线程继续复用，不重复发现配置。
- 发现接口不被旧版 CLI 支持时，保留进程级配置并继续问答，不修改全局文件。

继续保留同一个 ChatGPT 登录、Luna max、Fast、HTTP、论文原文、页图、页码证据规则、会话历史和只读权限。用户配置与生命周期 hooks 没有修改。

## 同条件测量

合成资料为 20 页重复的机器人 PD 控制说明，明确标注虚构、仅有仿真证据、没有未知负载鲁棒性结论。每次都提供 121 个原文分片和 1 个应用清单，覆盖 20/20 页；首问请求均为 95,217 字节。没有通过删论文或降低思考强度提速。

问题固定为：

1. 请用中文300字以内解释这篇论文的核心方法，给出页码。
2. 请用中文150字以内解释刚才这个方法的主要局限，给出页码。

首字时间从调用 `sendTurn` 前开始，到第一个实际回答的 `agentMessage/delta` 为止，不把等待提示或思考状态计作回答。

| 方案 | 首问首字 | 追问首字 | 额外工具调用 |
| --- | ---: | ---: | ---: |
| v1.2.4，本机当日配置 | 92.5 秒 | 20.5 秒 | 3 |
| 专用配置试验 | 13.7 秒 | 5.4 秒 | 0 |
| 最终代码，冷启动 1 | 11.1 秒 | 12.9 秒 | 0 |
| 最终代码，冷启动 2 | 10.0 秒 | 8.8 秒 | 0 |
| 恢复基线旧会话，保留原 ID 与历史 | 16.8 秒 | 8.3 秒 | 0 |

最终代码冷启动 2：进程初始化和模型目录约 2.1 秒；创建论文线程及发现配置约 0.4 秒；第一轮从发出问题到可见回答约 10.0 秒。没有 MCP 启动事件，没有记忆提示注入，也没有命令执行。保留的本机 hooks 约占每轮前置 0.4 秒及结束后 1 秒。

回答保留了 PD 比例项/微分项机制、仿真范围、未知负载证据不足、虚构基准声明和页码。单元测试继续核验原文逐字保留、信任级别、固定模型与 max、Fast 的实际 tier ID、只读权限、旧会话恢复；新增测试核验配置不变更全局对象、不复制 MCP 凭证、包含点号的服务名不会被误解释。

这些是本机少量合成文本试验，不代表每篇真实论文都能达到固定延迟。长对话、图像、复杂推理、网络和服务负载仍会波动；本次正式代码的两次新会话首字为约 10–11 秒，追问约 9–13 秒，尚不能承诺所有问题几秒内出字。旧版基线与之前 27–35 秒的记录不同，是当日 Codex 记忆/扩展环境的测量，不能直接当作跨设备性能比较。

本机原始测量记录：`F:/codex/tmp/paper-latency-data/transport-sept12-baseline.json`、`transport-sept12-optimized.json`、`profile-lean-skills-memory.json`、`profile-product-2.json`、`profile-product-resume.json`。

## 官方配置依据

[OpenAI 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)说明了 `memories.use_memories`、`memories.generate_memories`、MCP 的 `enabled`、技能的逐项启用配置及应用连接开关。[App Server 文档](https://learn.chatgpt.com/docs/app-server)提供线程创建/恢复时的配置覆盖能力。开关由 Paper Ocean 的 CLI 参数和线程请求传入，不写入用户的 `config.toml`。
